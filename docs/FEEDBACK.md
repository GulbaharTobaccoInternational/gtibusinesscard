# Appreciation delivery

The four permanent reactions submit only a reaction ID, company ID and UUID to `POST /api/feedback`. The UI shows only the approved temporary confetti (44 pieces, reduced-motion aware), with no selected checkmark, toast, confirmation or delivery claim. The copy is centered beside the whole icon/label group.

The route requires a verified Supabase session, active authorization, assigned company and same-origin bounded JSON. Employee identity comes from the current server-read authorization record, never from the card form or request. The database supplies event time. Client recipient, identity and timestamp overrides are rejected.

The fixed sender is `Mr Ghashi <notifications@auth.mrghashi.com>`. Every message targets both `slavomir.kluziak@gulbahartobacco.com` and `vinu@gulbahartobacco.com`, and includes the authenticated employee name/email, approved reaction label, selected company, UTC timestamp and website. `RESEND_API_KEY` is server-only. SMTP OTP delivery remains Supabase's separate existing configuration.

`feedback_deliveries` is a private-by-policy outbox with no client grants. The service-only queue_appreciation function locks the verified employee’s authorization row and checks their latest outbox event across companies and reactions. The first click in a rolling ten-minute window queues one message to both recipients. Later clicks still animate and create no delivery record. Retrying the original UUID can resume its existing delivery. The UUID is unique in the database and the Resend idempotency key is stable across retries. Delivery claims acquire a 40-second lease and recheck current active/company access. Next.js `after()` runs delivery after the HTTP response within the route's 30-second budget. Network, 429 and 5xx failures retry up to three total claims with short backoff and seven-second provider timeouts. Provider rejections and missing credentials never become success records. Logs contain event IDs, attempt counts and generic error codes, without identities, secrets or card data.

HTTP 202 acknowledges the click whether it queued an email or fell within the cooldown. Outbox `accepted` means Resend returned an email ID; it does **not** mean delivered to an inbox. Provider delivery logs or recipient confirmation are required to establish actual delivery. The supplied send-only key cannot read delivery logs.

For recovery after a process interruption, run `node --import tsx scripts/retry-feedback.ts` in a trusted environment with `.env.local` configured. Only pending/failed/expired-lease records younger than 23 hours and below three attempts are eligible; this stays within Resend's 24-hour idempotency retention. Permanent provider errors require operator correction. No scheduled job, webhook or new service is introduced. Keep delivery records only as long as needed for operational recovery; they are not card history or analytics.

Protocol references: [Resend send-email and idempotency headers](https://resend.com/docs/api-reference/emails/send-email), [Next.js after](https://nextjs.org/docs/app/api-reference/functions/after).
